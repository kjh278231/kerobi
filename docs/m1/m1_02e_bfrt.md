# M1-02e 검증 계약과 결과: kb2 피벗 21 진입 선택(BFRT `1c35c5`)

작성 기준은 [스프린트 검증 기준](../15_sprint_verification.md)이다. [M1-02d](m1_02d_tau.md)의 후속 조사이고, 사용자의 "다음 스프린트 진행" 지시로 착수했다(2026-11-11). M2는 다른 세션이 M2-06b-2와 shared를 먼저 점유해 [시작 절차](../handoff/README.md) §1-3 순서대로 M1을 골랐다.

## 1. 범위와 주장

- 작업 종류: 조사.
- 조사 질문:
  1. kb2 피벗 21(BFRT 코퍼스 호출 21)에서 원본은 열 25를 flip 없이 넣고, `tools/proto/bfrt.py`와 Rust는 열 4를 넣고 25를 flip한다. 반복 0–21 상태(statecmp)와 코퍼스 입력(α·d·vstat·bound·δ)이 같은데 원본이 25를 고르는 분기와 그 입력은 무엇인가.
  2. 같은 원인이 BFRT 코퍼스의 남은 불일치 18건(fit1d 12, tuff 4, kb2 1, stocfor1 1, [m1_notes §8.6](m1_notes.md))을 설명하는가.
- 착수 전 가설(H1, C만): `1c35c5` 재선별(C:805–870)의 |α| 문턱은 `max(1e-13·max|α|, |spx+0x438|)`이고, `spx+0x438`은 PIVOTTOL 상수가 아니라 행 거부 때 갱신되는 누적값이다(C:1265·1966·2181, `28c93` C:787, 0 초기화 `28c93` C:90·625, `1df51` C:59, `534f7` C:134). 기록 후보가 0이고 lo > 0이면 C:878부터 `cand[0..lo)`로 다시 고른다. 재선별 θ 초기값은 −1e100이 아니라 1패스의 진행형 문턱(`dVar110`)이다. 프로토타입은 셋 다 다르게 가정한다.
- 제외 범위와 후속:
  - Rust `bfrt.rs` 수정은 구현 작업(M1-02f, 새 행 제안)으로 나눈다. 이번에는 프로토타입(`tools/proto/bfrt.py`)으로 원본 코퍼스 대조만 한다.
  - 대체 경로 C:878 이후의 비용 이동(`a7b54f`·`a7b4d6` 난수)은 코퍼스에 RNG 상태가 없어 사건이 나오면 미검증으로 남긴다.
  - `0x2cc ≠ 0`(인공 bound 단계) 변형 루프(C:342–420)는 기존 코퍼스 범위 그대로 둔다.
- 선행: main `51e12e2`(M1-02d 병합 포함). 미커밋 선행 변경 없음.

## 2. 원본과 상태 경계

- Gurobi 13.0.3, `libgurobi130.so` SHA-256 `8e87fca221fdffc922331c8619426031b3e72dfd419446422f88af0cb0e98f9c`. Netlib 모델(Method=1, Presolve=0, Threads=1).
- 원본 위치: `1c35c5` `0xc74a0`(C 2337줄). 1패스 C:180–430, 판정 C:440–500, quickselect C:500–700, 교차 뒤 보정 C:740–770(`lo &= OptTol < d`), 재선별 C:790–870, 대체 경로 C:876–1000, 행 거부 C:1240–1270·1950–1970·2165–2185. `28c93` `0xc4fe0` C:80–92·615–628·770–790.
- 시작·종료 경계: `1c35c5` 진입과 반환(기존 `tools/trace_specs/bfrt_io.json` 경계). 진입에 `spx+0x438`(d), `spx+0x420`(i), `spx+0x430`(i)를 더 읽는다. 읽기 전용 훅이다.
- 입력 상태: 기존 코퍼스 필드(p2, p3, 이탈 행 XR, α SV:0x208, d AX:0x1e0, vstat AXI:0x168, l/u AX:0xa8/0xb0, `0x2cc`, `0x2a0`, `0x388`, `0x398`) + 위 세 필드.
- 출력: 반환값, 진입 열(`0x2fc`), flip 목록(OUT:3:4).

## 3. 비교 계약

| 필드·사건 | 의미·좌표·순서 | 비교 규칙·근거 | 캡처·재구성 방법 |
|---|---|---|---|
| `spx+0x438` | 호출 21 진입 값 | 비트. H1은 \|값\| > 0.6398945651894228(열 4의 \|α\|)를 요구 | 새 캡처 |
| 진입 열·flip 목록 | 호출마다 | 정확 일치(순서 포함) | 수정 프로토타입 vs 새 캡처 출력 |
| 기존 입력 필드 | 호출마다 | 새 캡처를 기존 코퍼스 필드로 투영해 기존 파일과 같음(비간섭) | 기존 `bench/oracle/bfrt_io` |

- 수치: 프로토타입은 원본 연산 순서로 계산하고 비트 비교한다.
- 재현성: kb2는 같은 설정으로 독립 프로세스 3회 캡처해 바이트 비교한다. 다른 모델은 1회 캡처 뒤 기존 코퍼스와 투영 비교로 재현성을 대신한다(기존 코퍼스는 이전 독립 실행이다).

## 5. 재실행 명령

- 원본 캡처: `tools/gurun.sh node tools/fn_trace.js <spec> <out.jsonl>`(spec은 `tools/trace_specs/bfrt_io.json` + 새 필드), Gurobi 한 프로세스.
