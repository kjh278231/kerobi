# 15. 스프린트 동작 동등성 검증 기준

이 문서는 모든 스프린트의 검증 계약과 완료 판정 기준이다. [1주 작업 목록](14_sprint_plan.md)의 개별 종료 확인은 이 기준을 구체화한다. 전체 풀이의 P0~P3와 관문 수치는 [포팅 가이드](10_porting.md)를 따른다. 구간 검증, 전체 관문, 시간 성능의 판정은 각각 기록한다.

## 1. 목표와 기준 원본

목표는 **같은 입력 상태에서 같은 판단·출력·상태 변경을 재현하는 것**이다. 동작의 최종 기준은 Gurobi 13.0.3 바이너리의 실제 실행이다. 디컴파일과 어셈블리는 제어 흐름·자료 구조·연산 순서를 복원하는 근거다. 디컴파일 표현과 실행 결과가 다르면 ABI·타입·호출 인자·훅 시점부터 확인한다. Rust 결과에 맞춰 기준값을 만들지 않는다.

같은 최적 목적, 같은 반복 수 또는 같은 시간만으로 내부 동작이 같다고 판정하지 않는다. 유한한 사례를 통과한 결과는 **명시한 입력 범위에서의 동등성 검증**이다. 모든 모델과 모든 실행에 대한 수학적 증명을 뜻하지 않는다.

검증할 구간을 상태 전이로 표현한다.

```text
원본:   입력 상태 S + 환경 E → 판단 D + 출력 O + 다음 상태 S'
구현:   같은 의미의 S와 E   → 판단 D + 출력 O + 다음 상태 S'
```

메모리 주소와 Rust 구조체 배치는 달라도 된다. 이후 연산에서 의미가 있는 순서·인덱스·값·RNG·상태는 같아야 한다. 필요한 입력 상태를 확보할 수 없으면 해당 구간의 동등성 검증을 아직 시작할 수 없다.

## 2. 세 검증 층

| 층 | 비교 경계 | 실행 시점 | 이 층만으로 주장할 수 없는 것 |
|---|---|---|---|
| 구간 | 함수 또는 독립 상태 전이의 전후 | 구현 작업마다 | 다른 구간과 연결한 전체 풀이 동등성 |
| 연결 | 연속된 몇 구간의 전달 상태와 사건 순서 | 연결부 변경 시 | 전체 모델 집합의 궤적과 성능 |
| 전체 | 원래 모델에서 상태·해·궤적·work | 마일스톤 관문, 영향 큰 회귀 | 관측하지 않은 내부 판단의 일치 |

스프린트마다 전체 E2E가 완성돼 있을 필요는 없다. 대신 구현 완료에는 해당 구간을 판별할 수 있는 원본 비교가 필요하다. 전체 검사를 실행할 수 있는데도 영향을 받는 회귀를 생략하면 이유와 미검증 범위를 남긴다. 구간 검사를 통과해도 전체 관문이 실패하면 각각의 판정을 그대로 기록한다.

P3 성능은 별도 측정이다. 구간이 달라도 성능 병목 조사를 할 수 있으나, 서로 다른 일을 한 실행의 시간 비율을 동일 동작의 성능 패리티로 보고하지 않는다.

## 3. 착수 전 검증 계약

작업 기록에 [검증 계약 양식](templates/sprint_acceptance.md)을 작성한다. 구현 작업은 비교 경계와 오라클 방법이 확정된 뒤 시작한다. 도구·ABI·경계가 미확정이면 먼저 조사 또는 오라클 구축 작업으로 분리한다.

| 계약 항목 | 필수 내용 |
|---|---|
| 작업과 주장 | 하위 번호, 조사·구현·검증 종류, 완료 후 주장할 동작과 제외 범위 |
| 원본 | 함수와 파일 위치, 필요한 어셈블리, 바이너리 버전·해시와 오프셋 해석 |
| 시작 경계 | 정확한 호출 전 또는 사건 시점, 입력이 만족할 전제 |
| 입력 상태 | 모델·basis·bound·후보·RNG·카운터·문맥 등 실제 읽는 상태 |
| 종료 경계 | 반환 또는 사건 직후의 시점, 조기 종료·오류·중단 포함 |
| 비교 대상 | 판단·출력·변경 상태·보존해야 하는 상태·사건 순서 |
| 비교 규칙 | 필드별 정확 비교·비트 비교·수치 비교와 그 근거 |
| 사례와 분기 | 일반·경계·동률·오류 등 포함할 분기와 실행 증거 |
| 오라클과 재실행 | 직접 호출·훅·저장 재생 중 방법, 기준 파일과 실행 명령 |
| 회귀와 완료 | 관련 연결 검사, 크레이트·통합 검사, 미검증 범위와 판정 방식 |

처음 정한 범위를 결과 확인 뒤 조용히 축소하지 않는다. 범위를 바꾸면 이유·제외 분기·후속 번호를 기록하고 기존 실패 사례를 보존한다. 비교 규칙을 바꾸는 경우에도 이전 결과와 변경 이유를 남긴다.

## 4. 같은 입력 상태의 조건

모델 파일과 Seed만 같다고 같은 입력 상태는 아니다. 구간이 읽는 상태를 조사해 함께 고정한다.

- 행·열 순서, 축약·원래 인덱스 매핑, 계수·bound·목적 상수·sense·타입.
- basis·열 상태, factor와 갱신 이력, 후보 목록과 동률 순서, incumbent·cutoff.
- 파라미터, RNG의 실제 상태와 소비 순서, 반복·노드·work·정체 카운터.
- worker·호출 문맥, 스레드 설정, 외부 라이브러리와 수치 환경.
- 타이머·자원 한도처럼 분기에 영향을 주는 외부 입력.

상태별 읽기·쓰기·보존 범위를 명시한다. 예를 들어 strong branching은 평가 결과뿐 아니라 임시 bound·basis의 복구도 검사한다. RNG를 소비하는 함수는 선택 결과와 종료 RNG 상태를 함께 비교한다.

구간 번호는 동일한 문맥의 호출로 식별한다. 예를 들어 모델·부모 노드·분기 방향·호출 순번을 사용한다. 같은 반복 수의 콜백이라도 초기화 도중과 반복 완료 뒤 상태가 다를 수 있다. 포착 시점을 원본과 Rust에서 같게 맞춘다.

## 5. 원본 구간을 실행하는 방법

| 방법 | 적용 대상 | 필수 확인 |
|---|---|---|
| 직접 호출 | 입력 구조를 재구성할 수 있는 복원·수치·선택 함수 | ABI, 인자·반환형, 자료 구조, 메모리 수명과 숨은 전제 |
| 정상 실행 전후 훅 | worker·basis·전역 문맥 의존이 큰 구간 | 실제 경로 실행, 전후 캡처 시점, 계측 영향 |
| 원본 상태 캡처 후 재생 | 반복 회귀와 원본 접근이 없는 컴퓨터 | 원본 생성 이력, 의미 기반 직렬화, 입력 재구성 |

직접 호출에서는 실행 중 라이브러리의 식별값을 검사한다. 다른 바이너리에 기존 오프셋을 적용하지 않는다. 주소·오프셋의 기준과 실제 매핑은 ELF·어셈블리 및 로드 정보를 대조한다. 함수 서명이나 SIMD 호출 인자가 불명확하면 합성 구조를 추측해 호출한 결과를 근거로 삼지 않는다. 호출 검사는 별도 프로세스로 격리해 충돌·메모리 오류를 판정한다.

정상 실행 훅은 실제 입력을 확보하기 좋다. 입력·출력만 읽는 계측을 먼저 사용한다. 상태나 함수 호출을 대체한 실험은 그 사실을 기록하고 정상 실행 사례와 구분한다. 계측이 호출 순서·시간 분기·스케줄에 영향을 주면 해당 측정의 주장을 제한한다.

캡처 파일에 원시 포인터만 저장해서는 재생할 수 없다. 배열·인덱스·링크·별칭 관계와 필요한 문맥을 의미 있는 형태로 저장한다. 원본 allocator·factor 객체 등을 복원할 수 없으면 독립 실행 가능한 더 큰 경계로 넓히고 작업을 다시 나눈다.

저장소의 기존 예시는 다음과 같다. 도구가 존재한다는 사실만으로 새 작업의 범위를 검증했다고 간주하지 않는다.

| 도구 | 방식과 범위 |
|---|---|
| `tools/mip_postsolve_oracle.py` | ctypes로 내부 `363164` 호출, 합성 복원 레코드 비교 |
| `tools/spx_oracle.py` | 정상 simplex 콜백에서 내부 작업 상태 캡처 |
| `tools/path_oracle.py` | basis 상태 변화에서 진입·이탈·flip 추적 |
| `tools/uncrush_oracle.py` | 복원 호출 경로의 계측. 패치한 호출을 기록에서 구분 |

Gurobi를 사용하는 캡처·호출은 기존 규칙대로 한 프로세스씩 실행한다.

## 6. 원본 자체의 재현성

새 오라클 경계는 먼저 같은 바이너리·입력·설정으로 원본을 독립 프로세스에서 3회 실행한다. 같은 설정과 경계를 검증한 기존 반복 자료가 있으면 그 자료의 식별값과 범위를 연결해 재사용할 수 있다. ABI를 확인한 순수 계산은 실행 주소나 객체 주소가 아니라 비교 대상 값을 확인한다.

다르면 차이가 생기는 최초 필드를 찾는다. 입력에 빠진 RNG·카운터·순서, 잘못 잡은 훅 경계, 타이머·병렬 스케줄, 계측 영향을 확인한다. 변동 필드를 통째로 제외하지 않는다. 그 값이 판단이나 다음 상태에 영향을 주면 선행 입력 또는 관측 경계를 바꿔야 한다.

타이머처럼 원본에 실제로 있는 비결정성이 원인이면 별도 계약으로 분리한다. 원인을 설명하지 못한 변동은 오라클 검증 미완료다. 세 번 일치했다는 사실은 모든 실행의 결정성을 증명하지 않으며 이번 환경의 재현성 증거로 남긴다.

## 7. 필드별 비교 규칙

| 필드 | 기본 규칙 |
|---|---|
| 상태·선택 인덱스·참거짓·개수·rank·정수 | 정확히 일치 |
| 후보·pivot·flip·cut·레코드 적용 순서 | 의미 있는 순서까지 정확히 일치 |
| RNG 상태·소비·결정적 카운터 | 정확히 일치 |
| 후속 분기에 쓰이는 부동소수 값 | 기본은 비트 비교. 같은 분기 결과만으로 전체 수치 동등성을 대체하지 않음 |
| 분기에 쓰이지 않는 수치 출력 | 원본 연산을 재현하는 경우 비트 비교. 정당한 수치 오차 비교는 사전 필드 계약 필요 |
| 메모리 주소·객체 식별자·비사용 padding | 주소 값 대신 인덱스·내용·필요한 별칭 관계 비교 |
| 타이머·병렬 사건 | §8의 별도 계약 |

수치 오차를 허용하는 필드는 `abs(a-b) <= atol + rtol * max(abs(a), abs(b))`처럼 비교식을 명시한다. `atol`·`rtol` 또는 ULP 한도를 필드별 근거와 함께 정한다. 목적값 검사에서 사용한 1e-6을 모든 내부 배열에 일괄 적용하지 않는다. 오차 이내라도 후보 순서·부호·정수성·허용오차 경계 판단이 달라지면 동작 동등성 실패다. 판단은 같아도 비트 기준 필드가 다르면 그 기준에서는 실패다.

NaN·무한대·±0·내부 무한대 sentinel은 일반 오차식으로 비교하지 않는다. 허용되는 값의 종류와 비트 요구를 계약에 적는다. 원본에서 NaN을 허용하지 않는 입력이라면 양쪽이 NaN이라는 이유로 합격하지 않는다.

메모리 배치 차이에 따른 정규화는 원래·축약 열 대응, 안정된 객체 식별 등 표현 차이에 한정한다. 후보를 정렬해서 순서 차이를 지우거나, 중복을 제거하거나, rhs·부호를 바꿔 실제 선택 차이를 숨기지 않는다. 동치인 cut 식만 검사한 결과는 수학적 유효성 검사이며 원본 생성 순서의 동등성은 별도로 판정한다.

## 8. 시간·work·병렬 실행

동작 비교의 기본은 Threads=1이며 벽시계 TimeLimit으로 같은 종료 지점을 만들지 않는다. 지정한 구간의 전후 경계, 특정 사건 문맥 또는 검증된 반복 단계에서 비교한다. NodeCount가 같아도 처리한 노드는 다를 수 있으므로 노드의 문맥과 상태를 함께 확인한다.

WorkLimit도 두 구현의 work 누적 규칙이 검증된 범위에서만 같은 진행량의 근거로 사용한다. work 미구현 상태에서 같은 WorkLimit의 결과가 다르다는 이유만으로 구간 로직의 실패를 판정하지 않는다. work 누락은 별도 작업으로 기록한다.

원본이 실제 경과 시간으로 분기하면 타이머 읽기와 분기 판단을 분리해 조사한다. 같은 타이머 값을 주는 실험이 가능하면 그 조건의 분기를 비교하되 조작한 실험임을 기록한다. 조작이 불가능하면 원본에서 관측한 조건·전후 상태를 비교하고 검증 가능한 범위를 명시한다. 동등성을 위해 원본의 시간 분기를 임의로 work 분기로 바꾸지 않는다.

시간 제한 작업은 만료 전·만료 진입·계산 중 만료, 보존해야 하는 부분 상태, 최종 상태·해·경계를 검사한다. 반환 시간이 정확히 TimeLimit과 같을 것을 요구하지 않는다. 실제 지연과 외부 감시 중단을 기록하고 허용 폭은 확인한 원본 중단 위치와 측정 근거로 정한다.

병렬은 단일 스레드 계약을 통과한 뒤 결정적 실행 단위·공유 상태·동기화 경계로 검증한다. 비결정적 스케줄의 사건 전순서를 그대로 일치시킬 수 있다고 가정하지 않는다. 허용할 차이와 보존할 불변조건을 사전에 명시하며 단일 스레드 검증 결과와 구분한다.

P3는 훅·상태 덤프 없는 실행으로 측정한다. 같은 기계·설정·입력·수치 환경과 부하 조건에서 반복 실행하고 실행별 원자료, 대표값과 분산을 기록한다. 반복 횟수·집계 방법은 측정 전에 정한다. P1·P2 집계가 같아도 관측하지 않은 추가 작업이 있을 수 있으므로 시간 차이를 곧바로 커널 속도만의 문제라고 단정하지 않는다.

## 9. 사례와 검사의 신뢰성

계약 범위에서 적용 가능한 일반 입력, 동점·정렬 경계, 허용오차 안·밖·경계, 빈 입력·고정·퇴화, 실패·중단·재처리 분기를 사례표에 적는다. 적용되지 않는 범주는 이유를 남긴다. 원본 분기별 실행 증거는 훅의 분기 식별, 함수 출력과 근거 등으로 연결한다. 사례 수만 많다는 이유로 분기 범위를 충족했다고 판정하지 않는다.

유효한 실제 입력에서 얻은 상태와 합성 입력을 구분한다. 내부 전제를 위반한 합성 입력이 일치해도 실제 모델에서 가능한 동작을 검증했다고 주장하지 않는다. 무작위 검사는 seed·생성 규칙·사례 수와 최초 실패 입력을 저장한다. 실패는 가능한 한 작은 입력으로 줄여 회귀에 남긴다.

검사가 틀린 구현을 잡을 수 있다는 증거도 하나 이상 남긴다. 이미 관측한 실패를 수정 전후로 실행하거나, 임시 복사본에서 선택 인덱스·임계값·순서 등 해당 동작의 오류를 넣어 비교기가 실패함을 확인한다. 단순 출력 파일 삭제나 실행 예외만으로 동작 비교기의 판별력을 검증하지 않는다. 고의 변형은 최종 코드에 남기지 않는다.

비교기는 첫 차이의 사례·사건·필드·인덱스·기준값·실제값·규칙을 출력하고 실패 종료해야 한다. 명령이 종료 코드 0으로 끝났다는 사실만으로 비교가 실행됐다고 판단하지 않는다. 사례 수·비교 필드·해당 분기 실행과 누락 필드를 확인한다. skip·xfail·오라클 충돌·기준 파일 누락은 통과 수에 포함하지 않는다.

## 10. 기준 자료와 다른 컴퓨터에서의 재생

기준 자료에는 최소한 다음을 연결한다.

- 하위 작업 번호, 상태 스키마 버전과 사례 식별자.
- Gurobi 버전과 실제 라이브러리 SHA-256, 캡처 도구 commit 또는 해시.
- 입력 모델·합성 입력과 그 해시, 파라미터·RNG·실행 문맥.
- CPU 아키텍처·OS, 수치에 영향을 주는 라이브러리·빌드·스레드 설정.
- 캡처·재생·비교 명령, 비교 규칙, 기준 자료 해시와 원본 반복 실행 결과.
- 원본 확인 위치, 포함 분기와 미포함 분기, 실제 사례인지 합성 사례인지.

원본 캡처→고정 기준 자료→Rust 재생→비교 결과로 출처를 추적할 수 있어야 한다. 원본 라이브러리가 없는 컴퓨터도 기준 자료와 필요한 입력이 있으면 재생 회귀를 실행할 수 있다. 새 원본 분기의 검증이나 기준 자료 재생성까지 가능한 것은 아니다.

기존 자료에 버전·해시 등 식별 정보가 없으면 그 한계를 기록하고 영향 범위를 확인한다. 새 바이너리·ABI·스키마를 사용하면 원본 재현성을 다시 확인하고 별도 기준 자료를 만든다. 실패한 기준값을 Rust 출력으로 덮어쓰거나 과거 실패 증거를 삭제하지 않는다.

권장 배치는 `bench/oracle/<작업번호>/`에 입력·원본 출력·manifest를, `docs/m*/`의 작업 기록에 계약·결과를 두는 것이다. 기존 도구의 저장 형식은 그대로 사용할 수 있다. 이 경로 규칙은 새 하네스 구현이나 공통 JSON 스키마가 이미 있다는 뜻이 아니다. ignore된 자료와 저장소 밖 자료는 인수인계 패키지에 포함했는지 확인한다.

## 11. 작업 종류별 완료 판정

작업 수행 상태와 동등성 판정을 따로 적는다.

| 작업 종류 | 완료 조건 | 동등성 주장 |
|---|---|---|
| 조사 | 계약의 질문에 근거로 답하고 필요한 상태·분기·미확인 범위·후속 작업을 특정 | 조사만으로 구현 일치 판정 불가 |
| 오라클 구축 | 입력·캡처 경계·원본 재현성·비교기의 오류 검출과 재실행 확인 | 구축한 경계와 사례 범위까지만 |
| 구현 | 계약 범위 사례·필드·분기가 원본 비교를 통과하고 관련 회귀·인수인계 완료 | 계약 범위 통과. 제외 범위는 미검증 |
| 검증 | 합의한 입력·설정·필드를 실행·분석하고 통과·실패·미검증을 모두 기록 | 실패 보고서 완성은 기능 합격과 별개 |

동등성 판정은 `통과`, `실패`, `미검증`으로 구분한다. 수치 계약을 통과한 경우 `수치 기준 통과`와 오차식을 함께 쓰고 비트 일치로 보고하지 않는다. 예외·근사·패리티 차이는 기록할 수 있지만 구현 동등성의 통과로 바꾸지 않는다.

구현 완료에는 다음이 모두 필요하다.

1. 사전 계약과 실제 변경 범위가 일치한다.
2. 실제 원본 실행에서 온 기준 자료와 같은 의미의 입력 상태를 사용했다.
3. 지정한 모든 필드·사례·분기가 비교를 통과하고 검사기의 오류 검출 증거가 있다.
4. 영향 범위의 회귀를 통과하고 실행하지 못한 검사는 명시했다. 핵심 원본 비교를 실행하지 못했으면 구현 완료로 판정하지 않는다.
5. 원본 파일·명령·결과·미확인 범위·후속 번호·commit 상태를 기록하고 인수인계를 갱신했다.

원본 접근 불가, ABI 미확정, 재현 실패, 기준 자료 부족, 범위 내 차이는 각각 원인을 적어 미완료로 둔다. 기간이 끝나면 결과와 남은 작업을 인계하고 필요한 경우 재분할한다. 이미 정한 범위에 실패 분기를 남긴 채 나머지만으로 전체 완료를 선언하지 않는다. 기존 작업에 새 기준을 적용할 때 과거 완료 이력을 삭제하지 않고 새 기준의 검증 범위를 별도로 평가한다.

## 12. 예: M2-03 자식 LP 무계

M2-03a는 `600d25` case 5의 직접 무계 확정 조건을 해독하는 조사다. 해당 필드·조건·실행 경계를 근거로 확정하면 그 조사 범위는 완료할 수 있다. 핵심 조건이 미확인인 채 시도 목록만 적으면 미완료다. MIP 전체 무계 동작이 검증됐다고 주장할 수는 없다.

후속 구현의 계약은 실제 자식 노드에서 들어간 LP 상태·부모 문맥·필요한 ray·domain을 입력으로, 노드 상태·재처리 여부·MIP 종료 상태·보존된 해와 경계를 출력으로 잡는다. 루트 무계 사례로 자식 경로를 대신하지 않는다. 직접 확정, 방향 검사 통과, 거부·보류처럼 범위에 포함한 분기를 원본에서 구분한다. 아직 원본 해석이 끝나지 않은 세부 조건은 이 문서에서 추정하지 않는다.

그 분기 하나의 구간 동등성을 검증한 뒤 worker의 상태 전달을 연결 검사한다. 전체 MIPLIB의 시간·상태·노드 수 비교는 이후 관문이다. 따라서 전체 E2E가 아직 다르더라도 검증한 구간을 범위 한정 완료로 남길 수 있다.
