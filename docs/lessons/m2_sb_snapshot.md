# SB 저장·복원 경계

- **SB bound setter `d8d5f` 반환은 모델 bound 복원 완료가 아니다.** C·캡처: 변경은 큐에 들어가며 `edd71`이 적용한다. 열 scale이 있으면 |값| < 1e30 요청을 scale로 나누므로 요청1이 내부8이 될 수 있다. setter 직후·flush 직후를 분리해 검사한다. (M2-06h-1, [근거](../m2/mip_sb_lp_snapshot.md))
- **`695bd7`은 up 결과가 1e100 이상이면 복구 뒤 down을 풀지 않는다.** C:660 `param_10[j] < 1e+100`이 down 진입 조건이다(asm 0x572b37 `comisd; jae` 기준이라 NaN이면 down으로 간다. 디컴파일 `<` 표기는 NaN에서 반대로 읽힌다). 후보 루프를 옮길 때 이 건너뛰기와 복구 순서(reset→restore→bound 복원 요청 뒤 판정)를 같이 옮긴다. (M2-06h-2, [근거](../m2/mip_sb_control_rust.md#6-실행-결과))
- **pk1 첫 후보 자료로는 목적 clamp의 base 선택을 두 상태 모두 판별할 수 없다.** 48방향 중 상태7은 dual==base 34·dual>base 8, 상태2는 obj>base 5·obj==base 1이다. clamp는 asm `maxsd`(디컴파일 `<=` 형태는 NaN에서 다름)이므로 이식은 asm 피연산자 순서를 따른다. 검증하려면 다른 후보·모델을 캡처한다. (M2-06h-2, [근거](../m2/mip_sb_control_rust.md#6-실행-결과))
- **Rust 변이 검사의 원문 패턴은 소스 수정 때 같이 깨진다.** `mip_sb_control_rust.py`의 mutant `old` 문자열이 소스에 없으면 assert로 멈춘다. 오류 처리 형태를 바꾸면 변이 표와 manifest(`--write-manifest`)를 함께 갱신한다. (M2-06h-2)
- **`695bd7`의 전파 경로(`local_90≠0`)와 비전파 경로는 bound·복구 줄이 다르다.** pk1 첫 후보는 모두 전파 경로(C:669–679, 772–781, 복구 루프 592–647·993–1047)였고, 복구는 엄격 부등일 때만 요청하며 work `param_12`에 6·개수를 더한다. 근거 줄은 실제 훅 경로(`6953ff`)로 확인하고 인용한다. (M2-06h-2 재검토, [근거](../m2/mip_sb_control_rust.md#2-원본과-상태-경계))
- **완료 선언 뒤 바꾼 코드는 독립 검토를 다시 받는다.** 06h-2는 첫 검토 뒤 `Unported`·변조를 추가하고 재검토 없이 병합했다가, 사후 재검토에서 clamp 미판별·근거 줄 오인용이 나왔다. 검토 기준 commit을 기록하고 그 뒤 diff가 있으면 재검토한다. (M2-06h-2)
- **`695bd7` 후보 루프는 사전 채움 추정치로 후보와 down을 건너뛴다.** 최적 방향 LP의 뒤 후보 해 v가 부모 해의 `floor+1e-10` 이하/`ceil−1e-10` 이상이면 그 방향 추정치를 `minsd(추정, obj)`로 줄이고, `(|parent|+1)·1e-15 > obj−parent`면 결과 칸을 parent로 채운다(asm 0x5727dd–0x5728d1). 두 추정치의 `628772` 점수가 best 이하면 후보 통째(tr12-30 3회), up 뒤 down 추정 점수가 best 이하면 down(20회)을 건너뛴다. 건너뛴 down 칸은 −1e100으로 남아 stall 판정에 들어간다. (M2-06h-3, [근거](../m2/mip_sb_loop_rust.md))
- **`6953ff` 전파의 bound 요청은 전파 함수 안에서 나오고 `695bd7`은 복구 요청만 낸다.** tr12-30은 방향 562회 중 459회가 변경 목록 > 1이다. 복구는 getter `115607`/`1157b8` 원래 값과 엄격 부등일 때만 요청하고 `work += 6·목록 길이`다. getter는 void라 반환 레지스터는 쓰레기다(캡처하면 반복 실행이 달라진다). (M2-06h-3)
- **`695bd7`의 "0회 분기" 대부분은 모델을 넓히면 자연 실행에서 난다.** 06h-3 3모델에서 0회였던 상태 3(down 1e100)·−1000·dual < parent·up 사전 채움이 MIPLIB 38모델 NodeLimit 300 탐색(모델당 수 초~수 분)에서 수십~수백 회 났다. −1000은 C:556–569에서 7·11과 같은 dual clamp다. 타이머 만료는 ran14x18-disj-8에서만 났다(조사에서 찾은 유한 예산은 루트 사전 SB `64da9f` C:911). 사례를 고를 때 가장 작은 캡처(markshare_4_0 29KB)를 먼저 찾는다. (M2-06h-4)
- **비전파 경로(`695bd7` N = NULL)는 VarBranch = 3의 `62a05d`(asm 0x538810 `xor %esi,%esi`)에서 관측했다.** 그 블록에 다른 진입 조건이 없는지는 미확인이다. 기본 설정 33모델에서는 비전파 0회였다. stride > 1은 `691b56`의 worker ≥ 2 경로뿐이라 Threads=1에서는 나지 않는다. (M2-06h-4)
- **`695bd7`의 타이머 만료는 별도 처리 없이 stall 종료와 같은 출구로 간다.** `adf2be` 반환 ≠ 0이면 `0x573567 je` 뒤 `0x57356d`로 떨어지고 stall·k ≥ n 종료도 같은 주소로 뛴다. 그래서 만료 뒤에도 flush(`edd71`)·부모 재풀이를 하고 그때까지의 배열을 돌려준다. `Unported`로 막아 둔 분기를 옮길 때는 먼저 원본 자료의 그 사건 뒤 단계 순서(`timer r=1 → flush → solve`)를 확인하면 이식이 한 줄로 끝나는지 바로 알 수 있다. 하네스에서 사례를 걸러내던 코드와 '여전히 거부되는지' 검사도 같이 지운다. (M2-06h-5, [근거](../m2/mip_sb_timer_rust.md#2-원본과-상태-경계))
- **`695bd7` 비전파 경로는 후보 열 자신의 bound를 `d8d5f`로 직접 요청하고, reset·restore 뒤 같은 쪽을 무조건 다시 요청한다(work 없음).** 복구 값은 후보 시작 때 LP 내부 bound(`+0xe8` 자료 `0x390`·`0x398`) × 열 배율이고 문턱(env `+0x2458`, 관측값 1e30) 밖이면 ∓1e100이다. 원래 bound getter는 전파 블록 안에서만 불려 비전파 묶음의 사전 단계는 `factorSave, save, input, attr`이다. 내부 lb가 −0.0이면 복구 요청도 −0.0이다(markshare_4_0). (M2-06h-6, [근거](../m2/mip_sb_direct_rust.md#2-원본과-상태-경계))
- **비전파 묶음에서 `boundwrite`를 요청/복구로 나눌 때 "다음이 flush"를 쓰면 틀린다.** 마지막 후보의 down 복구 바로 뒤가 종료 flush라서 복구가 요청으로 세진다. 직전 단계가 `restore`인지로 나눈다. (M2-06h-6, [§6](../m2/mip_sb_direct_rust.md#6-실행-결과))
- **`695bd7` 전파 모순은 MIPLIB에서 깊은 NodeLimit에서만 나고, 06h-4가 한도 초과로 못 잡은 모델에 있었다.** NodeLimit 5000 스캔에서 up 46회(csched007 41·csched008 1·neos-860300 2·neos-911970 2), down 1회(ic97_potential)였다. csched007은 NL 150, ic97은 NL 1050이 첫 모순을 포함하는 작은 한도다. up 모순은 목록 1(후보 열 자신, 이진)로 끝나고 up = 1e100, 복구 요청 뒤 풀이 없이 다음 후보로 간다. ic97 down 모순은 목록이 B·C·C(암시 bound 연쇄)다. (M2-06h-7)
- **연속 열 SB 후보는 presolve 뒤에도 남은 SOS의 연속 멤버에서만 나온다(`5d4427` 2군, `M+0x680`).** MIPLIB 38모델에는 SOS 절이 없어 0회가 당연하다. 빡빡한 용량의 SOS2 합성 모델(`tools/mip_sos_models.py`의 sos2_g40k5t)은 기본 설정에서도 루트 2묶음에 연속 후보 2개씩을 냈다. SOS1은 기본 설정에서 big-M 변환으로 SOS가 사라지고, `PreSOS1BigM=0`이면 남아 후보가 된다. (M2-06h-7)
- **`695bd7` up 모순 뒤에는 같은 후보의 down을 계산하지 않는다.** csched007 7회 모두 `prop out=1`(목록 = 후보 자신) → 복구 요청(값 −0.0) → poll → timer → 다음 후보의 up 순서였고 a는 초기값 −1e100으로 남았다. LP 풀이는 없다. (M2-06h-7, [근거](../m2/mip_sb_contra_cases.md#4-사례와-원본-자료))
- **workspace `+0x418` flags(byte[m+n])는 앞쪽 일부가 초기화되지 않은 힙 잔여값일 수 있다.** sos2_g40k5t 첫 묶음에서 바이트 2–5·9–11이 실행마다 달랐고(해제된 청크의 포인터·키로 추정) save/restore가 그대로 복사했다. MIPLIB 사례에서는 같았다. 3회 캡처가 이 요약 하나만 다르면 원시 바이트 probe로 위치를 보고 비결정 필드로 기록한다. (M2-06h-7, [§6](../m2/mip_sb_contra_cases.md#6-실행-결과))
