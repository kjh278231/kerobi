# M2-03d-7 검증 계약과 결과: B&B 노드 LP simplex ws의 빈 행 출처

작성 기준은 [스프린트 검증 기준](../15_sprint_verification.md)이다. 배경은 [M2-03d-6](mip_retry_bnb_node_lp.md) §6 C2다. 03d-6은 nidda 노드 16948 재풀이에서 simplex ws가 API LP에서 96행(R)을 비운 LP임을 캡처했지만 출처를 확인하지 못했다. 03d-6 인수인계의 제안 항목이고, 사용자의 "다음 스프린트 진행" 지시로 착수했다(2026-11-10).

## 1. 범위와 주장

- 작업 종류: 조사(원본 실행 훅으로 답한다)와 그 근거의 오라클 고정. Rust 솔버 코드는 바꾸지 않는다.
- 조사 질문(착수 시):
  - Q1. 노드 16948 재풀이의 `02f7e1` 반환 시 ws CSC(`ws+0x70/0x78/0x80/0x88`)와 b(`ws+0xa0`)는 D(`lp+0xe8`)의 `+0xf8/+0x100/+0x108/+0x110/+0x380`과 같은 메모리인가. 다르면 그 포인터를 가진 필드는 무엇인가. `08b2fe` 반환값은 `lp+0xe8`인가.
  - Q2. ws와 D의 열 길이·rhs가 처음 갈라지는 시점은 언제인가.
  - Q3. ws 열 길이를 줄이고 b를 0으로 두는 원본 함수와 그 조건은 무엇인가.
- 포함 사례: `neos-3754480-nidda`, 03d-5·03d-6의 H 설정 seed 1, 재풀이 노드 16948(`5ce67b` call 19901).
- 제외 범위와 후속:
  - Rust 재생(L2)과 `bnb.rs` 연결은 M2-03d-4다.
  - 행 선택 규칙(어떤 행을 고르는가)의 원본 대조와 Rust 이식은 이번 범위 밖이다. 규칙은 C로 읽은 내용만 §2에 적고, 대조는 후속 M2-03d-8(제안)로 넘긴다.
  - 2행 sense 변경(225, 375), 86행 cut 종류는 다루지 않는다.
- 선행: main `b5804da`. 미커밋 선행 변경 없음.
- 계약 변경(탐색 probe 뒤, 결과 판정 전): §6.1의 probe가 Q1에 답했다(ws 배열은 D 배열과 같은 메모리). 따라서 Q2의 전제("ws와 D가 갈라진다")는 틀렸다. Q2를 "D의 길이·rhs 배열이 언제, 누구에 의해 바뀌는가"로 고쳐 쓰고, 비교 계약을 §3의 M·B·L·X·S·P로 확정했다. 처음 계약의 "동일 상태(L)·재현(B)" 규칙은 그대로 두었다.

## 6. 실행 결과

### 6.1 탐색 probe(계약 확정 전)

- smoke(NodeLimit 3000)와 대상까지의 1회 실행에서 모든 기록 시점의 `08b2fe` 반환은 `lp+0xe8`이고 `lp+0xf8`·`lp+0xf0`은 null이었다. ws CSC·b 포인터는 D의 같은 필드와 같았다(별칭 5개 모두 같음).
- 대상 call 19901의 `02f7e1` 반환에서 D 길이 합과 ws 길이 합은 둘 다 1840이었다. 이때 D 해시(`aa359520-66a2a8de`)는 `cda5b` 진입 때의 03d-6 값과 달랐고, ws 해시는 03d-6 값(`daf530bc-1f6d7903`)과 같았다. 즉 D 배열 자체가 `cda5b` 진입과 `02f7e1` 반환 사이에 바뀐다. 이 결과로 `cda5b`의 호출 순서를 읽어 C:120 `10f448`을 찾았다.
- 03d-6의 갈래 두 개("`08b2fe`가 다른 자료를 돌려줌", "D 길이가 `02f7e1` 안에서 바뀜")는 둘 다 아니다. 03d-6 캡처에서 이미 ws가 있었으므로 `02f7e1`은 C:569에서 반환하고, 교체는 그 앞의 `cda5b` C:120에서 일어난다.

### 6.2 고정 캡처

- 실행 commit: 도구 `9ec8e61`. 실행 위치는 worktree `../rsolver-m2-03d-7`이다. 3회 모두 `DONE 8 32898`, 사건 4700개, 오류 없음이다. 세 파일은 바이트 단위로 같다.


- 변조 22종을 모두 거부했다. P 변조는 처음에 대상 뒤의 사건을 건드려 5종이 통과했다. 대상 이전 사건을 노리도록 고친 뒤 모두 거부됐다(§7 교훈).
- R의 출처: 노드 3966(깊이 11)이 다이브의 첫 노드다. call 19862 뒤 `5fb8ec` C:528이 직전 다이브 목록(101행)을 전부 재활성했다. 이어 call 19863·19864가 전체 LP(nnz 4955)로 노드 3966을 풀었다. 그 뒤 C:1856이 96행(모델 32·cut 64)을 비활성했고, call 19865가 줄인 LP(nnz 1840)로 같은 노드를 다시 풀었다(호출 순서는 probe의 호출별 nnz로 확인). 이 목록은 노드 16948(깊이 30, call 19901)까지 바뀌지 않았다. 따라서 R은 노드 16948이 아니라 노드 3966의 상태로 고른 행이다. 03d-6에서 R이 노드 16948 bound의 중복 행과 맞지 않았던 이유가 이것이다.
- 전체 실행 통계(top-level MIP, 끝까지): 대상 LP(lp 2, 재시작 뒤)는 deact 1135회·react_all 1135회이고, deact는 모두 `5fb8ec+0x37c9`, react_all은 모두 `5fb8ec+0x79e`다. 재시작 전 LP(lp 1)는 deact 10회·react_all 11회이고, 그중 1회는 재시작 `6a6563`(`0x5807b1`)에서 왔다. deact 한 번의 행 수는 4–189이고 노드 깊이는 대부분 9–16이다. `10e62f`는 0회다. 중첩 MIP에서도 deact 173회·react_all 175회가 있었다(재생 대상 아님).
- 재생 범위: 대상 LP의 X 목록 633단계를 순서까지 맞혔다. 행 삭제(D 행 수 감소) 뒤 빈 목록 전까지 15단계는 비교하지 않았다. 비교한 단계는 거의 모두 "react_all로 비움"과 "빈 목록에 deact 붙이기"다. 비어 있지 않은 목록에서 비어 있지 않은 목록으로 가는 단계는 15개이고, 그중 행을 뺀 단계는 0개다. 따라서 `edd71`의 "마지막 원소를 옮겨 빼기" 순서 규칙은 C만이다.
- 계측 무영향: L이 대상 call 19901까지 03d-6 캡처와 같은 D·ws 해시를 보여 준다. 그 뒤(실행 끝까지)의 통계는 3회 일치에만 기댄다.
- LP 번호는 heap 포인터의 첫 등장 순서로 매겼다([교훈](../lessons/tooling.md)은 이를 경고한다). 이번에는 3회 사건이 바이트 단위로 같고, 재생이 같은 번호의 사건만으로 목록을 이어 맞혔으므로 번호가 섞이지 않았다고 판단했다.
- 실행하지 못한 검사: 선택 규칙의 입력(노드 3966의 bound·slack·cut 속성)을 캡처하지 않았으므로 규칙 대조는 없다. DynamicRows=0 대조군도 없다. Rust·Python은 바꾸지 않아 해당 검사를 실행하지 않았다.
