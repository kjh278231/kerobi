# M2-03d-11 검증 계약과 결과: DynamicRows 관문 입력 오라클

작성 기준은 [스프린트 검증 기준](../15_sprint_verification.md)이다. 배경은 [M2-03d-8](mip_dive_rows.md) §6.3과 [M2-03d-10](mip_dive_list_rust.md) §7이다. 03d-8 `d:gate`는 관문 통과로 예측한 판정만 입력을 남겼고 실패는 첫 실패 절별 개수만 셌다. 그래서 03d-10은 관문을 이식하지 못했다. M2 인수인계의 첫 제안 항목이고, 사용자의 "다음 스프린트 진행" 지시로 착수했다(2026-11-11).

## 1. 범위와 주장

- 작업 종류: 오라클 구축. 원본 실행 훅으로 두 관문의 모든 판정(실패 포함)에서 절 입력의 원시 값과 결과를 캡처한다. 그 입력으로 C 규칙을 재구성한 Python 판정을 둔다. Rust 솔버 코드는 바꾸지 않는다.
- 완료 후 주장할 것: 계약 사례에서 C:526 재활성 관문과 C:1581 선택 관문의 판정마다 절 입력 값이 남는다. §2 규칙이 그 값에서 원본 결과(양성 훅으로 따로 관측)를 정확히 재현한다. 각 절이 실행에서 결과를 바꾸는지(판별력)를 절별로 보고한다. 03d-8 §6.3은 두 관문의 노드 조건을 횟수로만 맞췄다. 이번에는 `5fb8ec` 호출별로 대조한다.
- 포함 분기:
  - C:526(`0x510940`): DynamicRows(env+0x2b48)≠0, `I+0x2c`=`W+0x34`이면 `10e662`를 부른다.
  - C:1581(`0x512468`): DynamicRows≠0, `I+0x2c`=`W+0x34`, `I+0x28`=2, `I+0xa0`≠0, `I+8`≠0을 본다. 통과하면 `0x513078` 뒤에 `a7f0ad(lp)`=0, `a7f923(lp)`=0, `*(param_3+0x18)`<2를 본다(`0x513198`–`0x5131bc`).
  - DynamicRows=0 대조군(03d-8과 같은 설정).
- 제외 범위와 후속:
  - 관문 Rust 이식은 다음 하위 번호로 둔다.
  - `a7f0ad`·`a7f923`은 QP·QCP 판정(`re/notes/10_solve_driver.md`)이라 선형 MIP에서는 0으로 예상한다. 반환값은 캡처하지만 0이 아닌 사례(MIQP·MIQCP)는 만들지 않는다. 실행에서 갈리지 않으면 C만으로 보고한다.
  - `W+0x34`는 `6e8eb3`이 노드를 꺼낼 때 그 노드의 `I+0x2c`(깊이)를 쓴다(C:200–202, C:369–373). 이 출처는 C로만 기록하고 실행으로 대조하지 않는다.
  - `param_3+0x18`의 의미, DynamicRows=−1 자동 판정의 내부(env 값을 바꾸는 쪽)는 조사하지 않는다. 실행 중 env 값만 캡처한다.
- 선행: main `2bc84de`. 미커밋 선행 변경 없음.

## 6. 실행 결과

### 6.1 도구 문제와 탐색 sweep(판정 근거 아님)

- 첫 smoke(nidda H, NodeLimit 3000)는 첫 선택 직후 프로세스가 죽었다. 새 훅을 하나씩만 켠 실행(NodeLimit 200)에서 `0x510940`·`0x510961`·`0x51305f`는 정상이었고 `0x51319d`·`0x5131af`·`0x5131b7`·`0x5131c2`는 하나만 켜도 죽었다. 예외 처리기로 잡은 지점은 `5e7204`+7(`0x509c97`)의 주소 0x3220 읽기였다. `5e7204`의 인자는 `0x5131ef`에서 읽는 `(%rsp)`(`0x5130b0`에서 저장한 mip 포인터)다. Frida 객체형 `Interceptor.attach(addr, {onEnter})`는 대상을 함수 진입으로 보고 `[rsp]`(반환 주소 자리)를 바꾸는 것으로 보인다(관측: 이 칸이 살아 있는 구간에서만 죽음). 새 중간 훅을 함수형(probe) `Interceptor.attach(addr, function () {...})`로 바꾸자 정상 종료했고, NodeLimit 200에서 `b:*`·`d:*` 투영이 03d-8 도구 출력과 같았다. 03d-8 객체형 훅(`0x512468`·`0x513078`·`0x513951`)은 그대로 두었다.
- 첫 sweep에서 I의 노드 칸 검사가 많이 실패했다. `0x130(%rsp)` 노드를 `5fb8ec` 진입 때의 `*param_1`과 비교했기 때문이다. C:1577이 `local_68 = *local_58`로 다시 읽듯이 호출 중 `*param_1`이 바뀐다. 검사를 관문 시점의 `*param_1`과 비교하도록 고쳤다(판정 전, 도구 commit `f9c7349`).
- sweep: 도구 sha256 앞 16자리 `22af8e0e7a1d6120`(commit `f9c7349`)으로 `../re/bench/data/miplib` 38모델을 `{"NodeLimit":3000,"TimeLimit":30}`(Threads 1, Seed 0)로 1회씩 돌렸다. 판정은 `python3 tools/mip_dive_gate_check.py --sweep OUT`이다. 결과 파일은 저장소에 넣지 않았다(1회 실행, TimeLimit 사용).
  - 관문 평가가 있는 36모델에서 C:526 157,757회, C:1581 157,732회가 모두 I·R·P를 통과했다. enlight_hard(노드 0)·sp150x300d(노드 1)는 관문 평가가 0회다. 03d-8에서 이 두 모델의 선택이 0회였던 이유다.
  - env+0x2b48은 모든 평가에서 −1, `param_3+0x18`은 모두 1, `a7f0ad`·`a7f923` 반환은 모두 0이다.
  - C:1581 첫 실패 절은 깊이 145,381, 상태 3,989, 통과 8,362다. 깊이 절이 참인 평가의 상태 값은 2가 8,362, 4가 2,352, 5가 1,634, 1이 3(neos-4954672-berkel·neos-860300)이다. `I+0xa0` null 24,208회·`I+8` null 13,586회는 모두 앞 절이 이미 거짓인 평가였다. 통과 8,362회는 모두 `0x5131c2`까지 갔다.
  - 고정 사례가 상태 4·5 실패(gmu·assign)를 이미 덮는다. 상태 1은 '=2' 규칙에서 새 판별이 없으므로 사례를 더하지 않았다(§4 그대로).

### 6.3 관찰과 계약 변경

- 계약 변경(결과 확인 뒤): N은 처음 `b:*`·`d:*` 사건 전체의 바이트 일치였다. gmu에서 call 951에 `b:lpnew`가 하나 더 나왔고(LP 3개 대 2개) 이후 `lp` 번호가 1씩 밀렸다. 이 번호는 03d-7 `lpId`가 LP 포인터를 키로 매기는 값이라, 새 LP 객체가 이전 주소를 재사용했는지에 달렸다. 03d-8 도구를 같은 세션에 gmu로 1회 다시 돌리면 저장본과 바이트 단위로 같았다. 그래서 새 도구가 heap 배치를 바꾼 것으로 보지만, 주소 이외 사건은 모두 같다. N을 gmu에 한해 "`b:lpnew`와 `lp` 필드를 뺀 투영이 같다"로 바꿨다. nidda·대조군·assign은 바이트 일치를 그대로 요구한다. 다른 규칙은 바꾸지 않았다.
- 계약 변경(sweep 뒤, 고정 캡처 전): I의 노드 칸 대조는 처음에 진입 때 `*param_1`이었다. 첫 sweep에서 C:526 35,439회·C:1581 57,482회가 이 검사에 걸렸다. C:1577이 `*param_1`을 다시 읽는 것처럼 호출 중 노드 객체가 바뀌기 때문이다. 관문 시점의 `*param_1`과 비교하도록 바꿨다.
- 객체형 중간 훅 확인: 03d-8에서 이어받은 `0x512468`·`0x513078`·`0x513951`은 객체형이다(§6.1의 `[rsp]` 문제). 임시 복사본에서 이 세 곳까지 함수형으로 바꿔 네 사례를 1회씩 돌렸다. 사건 전체가 커밋된 run 1과 nidda·대조군·assign에서 바이트 단위로 같았고, gmu는 LP 번호만 달랐다(이 구성에서는 03d-8과 같은 LP 2개). 그래서 객체형 세 곳이 쓰는 `[rsp]`는 이 계약 사례의 사건에 영향을 주지 않는다. 복사본과 출력은 저장소에 넣지 않았다.
- `W+0x34`는 C로 `6e8eb3`이 노드를 꺼낼 때 쓴 그 노드의 깊이다. 관문의 `I+0x2c`=`W+0x34`는 "지금 노드가 방금 꺼낸 노드와 같은 깊이"이고, 실행에서는 다이브 첫 노드에서 참이었다(03d-7). 쓰는 쪽은 실행으로 대조하지 않았다.
- top-level C:526 참 횟수는 03d-8 §6.3의 횟수 대조(nidda 1146, gmu 74, assign 66+3)와 같고, 이번에는 호출별로 맞췄다.
