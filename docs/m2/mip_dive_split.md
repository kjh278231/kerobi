# M2-03d-13 검증 계약과 결과: `10f448` 분할 순서 오라클

작성 기준은 [스프린트 검증 기준](../15_sprint_verification.md)이다. [M2-03d-10](mip_dive_list_rust.md) §7의 후속 제안("분할 순서 오라클")이고, 사용자의 "다음 스프린트 진행" 지시로 착수했다(2026-11-11). M2가 미점유라 시작 절차 순서대로 골랐다.

## 1. 범위와 주장

- 작업 종류: 오라클 구축.
- 조사 질문: `10f448`이 사본을 새로 만들 때(X≠0, 참조수 X+0x1c=0, 만듦 표시 X+0x18=0으로 진입) D 열의 ind·val을 어떤 순서로 제자리 분할하는가. 03d-10은 대상 노드 D가 이미 분할돼 있어 교환이 0회였고, "두 포인터 교환을 안정 분할로" 바꾼 변이를 거부하지 못했다.
- 완료 후 주장할 것: 네 사례(03d-11과 같은 입력·설정) 각 3회의 모든 재생성 호출에서 진입 시 D(열 시작·길이·ind·val), 행 위치(X+0x10), 반환 시 ind·val·줄인 길이(X+0x28이던 배열)·rhs 사본을 캡처했고, C 열 루프를 옮긴 Python 규칙이 모든 호출의 결과를 비트 단위로 재현한다. 원본이 실제로 교환한 호출과, 두 포인터 결과가 안정 분할과 다른 열이 있다.
- 포함 분기: 재생성(교환 있음·없음), 참조수>0 또는 만듦 표시=1로 들어와 다시 만들지 않는 호출(개수만), X 없음(개수만), 세 호출자(`c3d0d`·`cda5b`·`390989`, 반환 주소로 구분), 모든 MIP 깊이.
- 제외 범위와 후속:
  - Rust `RowList::swap_in` 재생 대조는 이번 판정에 넣지 않는다. 후속 번호(제안 M2-03d-14)로 넘긴다.
  - 재생성 사이에 D를 바꾸는 쪽(cut 추가 등)의 정체와, 다음 재생성 진입 D가 앞 재생성 결과와 같은지(누적)는 관측 개수만 적고 판정하지 않는다.
  - `10f5ae`, `edd71`·`dcd29`·`db102`·`fbf68`의 만듦 표시 해제 조건은 다시 대조하지 않는다(03d-10).
- 선행: main `7a4af88`(M1-02b 병합). 미커밋 선행 변경 없음. 03d-11 캡처 `bench/oracle/mip_dive_gate/`(manifest `bench/oracle/mip_dive_gate_manifest.json`)를 비간섭 기준으로 쓴다.

## 2. 원본과 상태 경계

- Gurobi 13.0.3, `libgurobi130.so` SHA-256 `8e87fca221fdffc922331c8619426031b3e72dfd419446422f88af0cb0e98f9c`.
- 원본: `10f448` `0x1a31c0`(`re/decomp/c/001a31c0_PRIVATE000000000010f448.c`, 116줄). 호출자 `c3d0d` `0x14acb0`, `cda5b` `0x153cc0`, `390989` `0x38c5f0`(`tools/dc.py 10f448`).
- C로 읽은 동작(인자 param_1 = D):
  - X = D+0x140. X≠0이고 X+0x1c를 1 올린 값이 1일 때만 동작한다.
  - X+0x18 = 0이면 열 j = 0..D+0xc마다 s = D+0xf8[j], e = s + D+0x100[j] − 1. 앞 포인터 a는 위치(X+0x10)[ind[a]] < 0인 항목을 건너뛴다. 위치 ≥ 0(목록 행)을 만나면 뒤 포인터 b를 위치 ≥ 0인 동안 내리고, 위치 < 0인 b를 찾으면 a<b일 때 ind·val(D+0x108·D+0x110)을 맞바꾸고 a+1, b−1 한 뒤 다시 앞 포인터로 돌아간다. X+0x28[j] = a − s.
  - D+8 행 수 > 0이고 X+0x20 ≠ D+0x380이면 rhs를 X+0x20으로 복사하고, 목록(X+8, 개수 X+0)의 행을 +0으로 둔다. X+0x18 = 1.
  - 끝에 D+0x100 ↔ X+0x28, D+0x380 ↔ X+0x20 포인터를 맞바꾼다.
- 시작 경계: `10f448` 진입. 종료 경계: `10f448` 반환. 조기 반환(X 없음, 참조수가 1이 아님)은 개수만 센다.
- 모델·설정: 03d-11과 같은 네 사례(`tools/mip_dive_gate_runs.sh`). nidda H seed 1(NodeLimit 32898, Presolve 0 등), 같은 설정에 `GURO_PAR_DYNAMICROWS`=0(대조군), gmu-35-40·assign1-5-8 기본 설정(NodeLimit 3000). Threads 1, TimeLimit 없음.
- 입력으로 읽는 상태(진입): D+8 행 수, D+0xc 열 수, D+0xf8 열 시작(i64), D+0x100 길이, 열마다 [s, s+len)의 ind·val, X+0x10 위치(행 수만큼), X 목록, X+0x18, X+0x1c, D+0x380 rhs와 X+0x20·X+0x28 포인터.
- 출력(반환): 같은 범위의 ind·val, D+0x100이 된 배열(진입 X+0x28과 같은 포인터인지)의 값, D+0x380이 된 rhs 사본, X+0x18·X+0x1c.

## 3. 비교 계약

새 도구 `tools/mip_dive_split.js`는 `tools/mip_dive_gate.js`(03d-11)를 복사해 `0x1a31c0`의 기존 리스너 하나에 새 기록을 더한다(같은 주소 리스너 하나 규칙). 새 사건은 `s:` 접두어이고, 새 코드는 `lpId`를 부르지 않는다(`b:lpnew`를 보내 투영을 바꾸므로). 자료량을 줄이려고 진입 D가 같은 D 포인터의 직전 재생성 반환 내용과 정확히 같으면(내용 전체 비교) 그 사건 번호만 적고, 아니면 전체를 적는다. 반환 시에는 바뀐 열의 ind·val과 줄인 길이 전체를 적는다(03d-8 `d:sel`의 bound 차분과 같은 방식).

`tools/mip_dive_split_check.py`가 판정한다. 하나라도 실패하면 종료코드 1이다.

| 검사 | 규칙 |
|---|---|
| M 입력 | 12개 캡처의 바이너리·모델·도구 SHA-256, 파라미터, 출력 줄이 manifest·사례표와 같다 |
| B 재현 | 사례마다 3회의 사건 열이 완전히 같다 |
| N 비간섭 | `s:` 사건을 뺀 사건 열이 같은 사례의 03d-11 run 1 캡처와 완전히 같다 |
| X 일관성 | 재생성마다 진입 참조수 0·만듦 표시 0, 반환 참조수 1·만듦 표시 1, 반환 D+0x100 = 진입 X+0x28 포인터, 위치와 목록이 서로 맞다(위치≥0 ⇔ 목록에 있음, 목록[위치[r]] = r). 참조한 이전 사건이 같은 D의 앞선 재생성이다 |
| R 규칙 | 재구성한 진입 D에 §2의 C 열 루프를 적용한 결과가 반환 ind·val(val은 위 계약 변경대로 재구성)·줄인 길이와 모든 열에서 같다. rhs 사본은 진입 rhs와 목록 행에서만 다를 수 있고 그 값은 +0 비트다 |
| T 목표 | 세 양성 사례 각각 재생성 ≥ 1. 세 사례 합계로 교환이 있는 재생성 ≥ 1, 두 포인터 결과가 안정 분할(비목록 항목 순서 유지, 목록 항목 순서 유지)과 다른 열 ≥ 1. 하나라도 0이면 실패 |
| C 대조군 | DynamicRows=0 사례는 재생성 0, 참조수 진입 사건 0(X 없음만) |
| K 개수 | 사례별 재생성·교환 재생성·안정 분할과 다른 열·교환 2회 이상 열·전체 기록 수를 출력한다. 첫 공식 캡처 뒤 값을 이 문서에 고정한다(회귀 기준, 판정 근거 아님) |

- 계약 변경(탐색 캡처 뒤, 공식 캡처 전):
  - N은 처음 "`s:` 사건을 뺀 사건 열 전체 일치"였다. 탐색 1회에서 nidda만 그대로 같았다. gmu·assign은 `b:lpnew` 하나의 `is_node_lp`(직전 solve의 lp 주소와 같은지)가, 대조군은 `b:lpnew` 하나의 유무가 달랐다. 대조군에서 그 뒤 4만여 건이 다른 것은 사건 위치가 밀린 것이다. 두 값 모두 `lpId`가 LP 포인터로 매기는 번호와 주소 비교라 heap 배치에 달렸다(03d-11 §6의 gmu 예외와 같은 원인). N을 네 사례 모두 "`s:`·`b:lpnew`·`lp` 필드를 뺀 투영이 같다"로 바꿨다. 이 투영으로 탐색 네 사례가 모두 같았다.
  - 자료량 때문에 반환 val은 비트 값 대신 훅 안에서 "반환 val[k] = 진입 val[src]"가 아닌 항목 수(`val_moved`)로 적는다. 검사기는 반환 val을 진입 val과 위치 치환(k←src)으로 재구성한다. 따라서 val이 ind를 따라 움직였는지는 훅의 비트 비교가 근거이고, 검사기는 `val_moved`=0을 확인한다. 줄인 길이는 진입 길이와 다른 열만, rhs 사본은 다른 행 번호와 +0이 아닌 값만 적는다.
- 정수·순서는 정확 비교, val·rhs는 u64 비트 비교. 허용오차 없음. NaN·무한대는 별도 처리하지 않는다(비트 비교).
- 시간·work: `10f448`에 work 증가가 없다(C). NodeLimit만 쓰고 TimeLimit은 쓰지 않는다.
- 재현성: 독립 프로세스 3회 바이트 동일(B)과 03d-11 투영(N).
- 규칙 변이(R을 변이 규칙으로 돌렸을 때 실패해야 함): 안정 분할, 앞으로 찾아 바꾸기(목록 항목을 그 뒤 첫 비목록 항목과 교환), val 미교환. 줄인 길이에 원래 길이를 쓰는 변이, rhs 0 생략도 넣는다. 거부되지 않는 변이는 결과에 "판별 안 됨"으로 적는다. 안정 분할·val 미교환·원래 길이 변이가 거부되지 않으면 실패다.
- 자기검사(`--self-test`, 메모리 변조 각각이 거부돼야 함): 바이너리 해시 0, 사건 비우기, run 2 한 사건 변경, 투영 차이(`g:` 사건 하나 삭제), 양성 사례 `s:build` 전부 삭제(T), 바뀐 열 ind 두 칸 교환, val 한 비트, 줄인 길이 +1, 위치 하나 반전, 참조 번호 변경, 대조군에 재생성 추가, rhs 사본 한 행 비영.
